.\.venv\Scripts\python.exe -X utf8 desktop\build.py --qa --no-zip --mcp-only --output release\language-learning-qa\Tulpa

分区端到端合成样本：A账号/甲群完成表达与黑话阶段 → A账号/乙群空库 → B账号/甲群空库 → 伪造A来源及迟到任务拒绝 → 返回A账号/甲群原记录和计数保留。检查了返回材料、记录及候选，未用 UI 显示代替存储验证。

成本样本：71条合成表达，100次同计划缓存读取约82毫秒，50候选的测试载荷4,517字符，远端调用0。该数字仅描述此机器的小样本，不是大规模吞吐保证。实际无向量服务时最多10个候选；没有逐消息模型调用。

## 真实模型验收

使用本机既有 DSH `0.2.0-rc.2` 的官方工具与 LLM 运行时，既有 `deepseek-official/deepseek-flash`、低推理强度。临时验收驱动只准调用学习查询/领取/提交，不具备聊天发送工具，不修改持久模型配置。

| 材料 | 调用与材料量 | 审核结果 | 实际采用 |
|---|---|---|---|
| 20条合成实时消息 | 提取和复核各1次，共约41.2秒；材料合计6,453字符；提供商报告总tokens 15,861 | 5条表达候选，接受2、拒绝3；20个黑话候选，确认0 | 表达不足10条，未供回复使用 |
| 用户启用后收到的12条真实群消息 | 提取和复核各1次，共约40.6秒；材料合计3,977字符；提供商报告总tokens 13,433 | 5条表达候选，接受4、拒绝1；17个黑话候选，确认0 | 本群未开启采用降级结果，且表达不足10条，未供回复使用 |

审核拒绝的真实样本涉及从一句话推断群友亲疏关系：模型认为来源不足，因此没有入库。真实原文、候选逐项对照和完整模型结果只保存在本机私人验收目录，未加入源码或公开报告。合成样本也发现提取会加入缺少来源支持的语气标签；单独复核确实排除了部分此类推断，不能据此保证今后每条审核都正确。

两个实验都标为 `independence=degraded`：是不同模型调用，但后续阶段保留顺序上下文。未声称实现严格隔离的“无上下文”推理。黑话仅走完候选积累，真实样本没有达到4个批次；三个释义阶段和4/8/25/100的完整运行已由合成响应验证，真实模型的黑话确认质量仍未验证。

## 发现的问题和限制

- 首次合成真实模型试验中，复核返回无法解析的 JSON；结果没有入可用库，状态保留为有限重试。随后仅在临时验收驱动将输出预算从4,000调到8,000后跑通；不能据此断言所有非法 JSON 都由截断导致，也没有修改用户模型配置。
- 最初回归发现未启用学习时的额外数据库访问影响了一个紧时序测试；现已使用启用/绑定内存缓存，关闭功能时接收路径不访问学习库，回归通过。
- 局部处理过期 READY 计划对学习领取的阻塞；未改动此前暂缓的回复相关性、收齐消息或发送算法。
- 当前没有现成 embedding 配置，实际采用 count 加权路线。受作用域约束的可选检索器以 fixture 验证了50条上限，不代表上线了向量服务。
- 没有活跃宿主继续领取阶段，就不会继续调用模型。服务端不能证明宿主真的清空上下文，也不能强制中断宿主推理；换群/账号要求新的 MCP 连接和宿主对话。
- 真实样本尚未实际采用学到的表达，不能宣称小鲸鱼已经变自然、识别黑话更准或回复速度改善。自然程度和模型选取质量需要后续人工体验。
